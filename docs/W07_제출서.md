## 1. 문제와 전문성 확장 요약

| 항목 | 작성 내용 |
| --- | --- |
| 결과물 이름 | 관련 거래처 판매장려금 통제 데스크 — 장려금 지급 전 관련자 판정 · 결재 경로 · 미수채권 상계를 한 흐름으로 처리하는 AI 기반 운영 시스템 |
| 선택한 사용자 · 의사결정 | **영업지원팀**이 대상월 장려금을 접수해 전결할지 상신할지, **영업임원**이 상신 건을 승인 · 반려할지, **재무**가 지급 전에 연체 채권과 상계할지 · 얼마를 상계할지, **내부감사**가 과거 지급의 결재 단계가 맞았는지를 결정한다. |
| 현재의 어려움 | 규정은 "거래처별 월 지급액 200만원 이하는 영업지원팀 전결, 동일 관련자는 합산하여 한도 적용"(approval_authority_policy)인데, 원본 지급 기록은 **건별 금액만 보고** 전결됐다. 같은 대표자 · 주소 · 계좌를 쓰는 관련 거래처 G1(D-011 · D-024 · D-037)은 1~5월 매달 406만~487만원을 받았지만 건마다 200만원 이하라 **15건 22,238,349원이 영업임원 승인 없이 전결 지급됐다**[원본]. 같은 G1 은 120일 넘은 연체 채권을 갖고 있는데 장려금은 현금으로 나갔다. 관련자 판단 정보(실입금계좌)가 재무 파일에만 있어 영업 결재 화면에 보이지 않는 **정보 공백**과, 영업(대리점 관계) · 재무(채권 회수)의 **부서 간 충돌**이 있다. |
| 기업 운영 안에서의 연결 | 출발: Corevia 의 대리점 마스터(`m_agency_cv`) · 입금 기록(`fin_collection_history_cv`) · 장려금 지급(`sales_rebate_payment_cv`) · 미수채권(`fin_ar_aging_cv`)[원본]. 시스템 역할: 장려금 지급 직전의 **통제 지점**. 앞: 영업 실적 마감(장려금 산정). 뒤: 재무 지급 · 채권 회수, 감사 사후 검토. 부서 간에는 승인 요청 · 상계 제안 · 부서별 작업(Task)으로 정보와 일을 넘긴다. 확장 가능한 연결: 마스터 정정 신고(대리점 → 영업지원팀), 은행 회신, 대리점 소명 · 상계 동의. |
| 주업무의 시작과 종료 | **시작**: 대상월(2026-06) 장려금 40건 접수(`미지급`[원본] → 시스템 상태 `미접수`[가정]). **분석 · 판단**: 관련자 그룹(코드) → 그룹 월 합산과 최소 결재권자(코드) → AI 추천 · 가드 → 사람 결재. **종료**: 지급완료 · 상계완료 · 지급보류(소명 대기) · 재검토필요 중 하나의 업무 상태와, 그 상태가 만든 부서 작업 · 이력. |
| 본인의 관심 · 전문성 | 자바 백엔드 부트캠프와 LangChain 과정에서 배운 상태 머신 · 트랜잭션 · LLM 에이전트 설계를 내부통제에 적용했다. "AI 는 판단 · 추천만, 결재권자는 코드가 정하고 AI 는 결재 단계를 올릴 수만 있다"는 원칙을 가드 코드로 강제하고, LangGraph 의 재개 값 저장 특성(재개 값을 받는 순간 체크포인트에 남는다)을 시험으로 확인해 "서비스가 먼저 검사 · 상태 변경 → 통과했을 때만 그래프 재개" 순서를 만들었다. |
| 필수 전문성 확장 | **지급 전 미수채권 대조와 상계[가정]**. 관련자 그룹 건이 승인되면 같은 그룹의 90일 초과 연체 채권[가정 기준]을 조회해 상계 한도(코드)를 계산하고, AI 상계액 추천[주장] → 재무 결정 → 대리점 동의[모의] → `AR_ADJUSTMENT` 로 채권 잔액 조정 · 지급액 감액(원본 잔액은 그대로)까지 처리한다. 필요 이유: G1 은 장려금을 받는 동안 미수 48,481,080원 중 120일 넘은 연체 5건을 갖고 있다[원본]. 사용 위치: `backend/app/services/offset.py`, `agents/offset_advisor.py`, API `POST /api/offsets/{id}/recommend · decision · agency-consent`, 화면 건 상세 "상계 검토" 칸. |
| 영향받는 다른 부서의 목표 · 제약 | **재무**: 연체 채권 회수(목표), 지급 지시는 재무만(권한). **영업**: 대리점 관계 유지(목표) — 상계는 관계 부담. **내부감사**: 결재 권한 준수(제약) — 과거 전결 위반 확인. |
| 다른 부서 영향의 실제 반영 | 상계 제안이 생기면 영업지원팀에 "상계 영업 의견" 작업이 열리고, 영업이 대안(전액 상계 · 부분 상계 · 지급 후 회수 약정)을 낸다[주장]. 그 의견이 AI 추천의 입력과 재무 결정 화면의 처음 값에 들어가고, 재무가 "지급 + 회수 약정"을 고르면 전액 지급 + 재무 "회수 약정 관리" 작업이 생긴다. 재무 결정이 영업 대안과 같은지(`sales_followed`)가 남는다. 감사는 "사후 검토 실행"으로 1~5월 위반 15건마다 작업을 받는다. |

전체 23개 표, ERD 는 [`docs/architecture.md`](architecture.md) 4장.

**핵심 관계와 연결 기준**
- 대표자 · 주소 · 계좌 중 **2개 이상 같으면 관련자, 1개면 정황**. 계좌는 등록계좌 + 실입금계좌 묶음을 속성 하나로 센다(공유계좌 하나가 "2개 일치"로 부풀지 않게). 정확한 문자열 비교, 지금 유효한 속성만. 관련자 쌍을 전이로 묶어 그룹(G1 = D-011 · D-024 · D-037)을 만든다. D-034–D-041 은 대표자만 같아 정황(접수 때 영업지원팀 소명 작업만 생기고 지급은 막지 않음).
- 결재 판정 단위 = 그룹(그룹이 없으면 대리점 혼자), 대상월 `period_ym` 기준 합산, 반려 건 제외.

**상태 · 적용 시점 · 담당자 · 승인권한**
- 건 상태 14개: 미접수 · 접수 · 관계확인 · 전결대기 · 상신대기 · 소명대기 · 지급보류 · 승인 · 반려 · 상계검토 · 지급지시 · 지급완료 · 상계완료 · 재검토필요. 전이표는 데이터(`services/claim_state.py`), 상태를 바꾸는 길은 `transition` 하나이고 매 전이가 이력 한 줄과 부서 작업을 만든다. 상태도는 [`docs/architecture.md`](architecture.md) 5장.
- 승인권한: 그룹 월 합산 2,000,000원 이하 영업지원팀 전결, 초과 영업임원[원본 규정]. 지급 지시 · 상계 결정은 재무, 소명 확인 · 정정 적용은 영업지원팀, 사후 검토는 내부감사. 권한 부족은 403, 상태 충돌은 409.

**판단에 사용하는 규칙과 제약**
- 최소 결재권자는 코드(`services/approval_authority.py`)가 계산하고, AI 가 더 낮은 결재권자를 말하면 가드가 코드 값으로 올려 고정 · 기록한다(내리지는 못함).
- AI 출력과 다른 결정은 사유가 있어야 한다(422).
- 상계 한도 = min(남은 지급액, 그룹 연체 잔액 − 같은 그룹 열린 제안 몫), 대상은 관련자 그룹 건 · 90일 초과 연체[가정].
- 지급 지시는 승인 건 · 계좌오류로 보류된 건 · 상계가 끝난 상계검토 건만. 증빙 부족 보류 건은 소명을 건너뛰어 지급될 수 없다.

**업무모델이 조회 · 계산 · 판단 · 승인 · 후속 작업을 연결하는 위치**: 접수(`services/intake.py`) → 판정(`approval_authority.py`) → AI 검토(`agents/graphs/claim_review.py`) → 결재(`services/approval.py`) → 상계(`services/offset.py`) → 지급(`services/payment.py`). 변경의 영향은 정정(`services/master_change.py`)이 그룹 새 버전을 만들고 소속이 바뀐 대리점의 돈이 안 나간 건을 재검토필요로 돌린 뒤, 결재 대기 건만 코드가 바로 재판정한다.

**업무 흐름에서 바꾼 것과 원본 제약 유지**: 원본 업무 지도(`Business_Process_Map.md`)에는 장려금 흐름이 따로 없고, 규정은 `approval_authority_policy.md` "판매장려금 지급 한도"에 있다 — "거래처별 월 지급액 2백만원 이하는 영업지원팀 전결, 초과 시 영업임원 승인, 동일 관련자(대표자 · 주소 · 정산계좌 2개 이상 일치)는 합산하여 한도를 적용, 지급 전 관련자 그룹 여부를 확인"[원본]. 원본 지급 기록은 이 합산 확인 없이 건별로 전결된 상태다. 시스템은 이 규정을 그대로 코드로 옮겨 **지급 전 관련자 판정 → 그룹 합산 → 결재권자 배정**을 강제하고(한도 · 권한 값은 바꾸지 않음), 그 앞뒤에 **상계 검토**(지급 전)와 **소명 → 재판정 → 재상신**(반려 뒤)을 더했다. 정산계좌는 등록계좌와 실입금계좌를 함께 본다(원본 입금 기록에 등록계좌와 다른 실입금계좌가 있어서).

## 3. 대표 실행 사례

모든 사례는 배포 앱의 **시연 패널**(역할 "시연 관리자")과 건 상세 화면에서 다시 실행할 수 있고, 같은 흐름이 자동 테스트로 고정돼 있다(pytest 447개).

- **계획 · 작업 · 상태가 생성 · 갱신되는 위치**: 매 상태 전이가 `event_log` 한 줄과 부서 작업(`task`)을 만든다(예: 승인 → 재무 "지급 실행", 상계검토 → 재무 "상계 검토" + 영업지원팀 "상계 영업 의견", 소명대기 → 영업지원팀 "소명 요청", 지급지시 → 지급보류 → 재무 "지급 계좌 확인"). 건이 상태를 떠나면 그 작업은 자동으로 닫힌다. 화면: 처리함 · 작업 · 이벤트 이력.
- **운영 중 AI 의 역할** — AI 는 판단 · 추천만 하고 결정 · 상태 변경은 사람과 코드가 한다:

| AI | 입력 → 출력 | 사람 · 도구 연결 |
| --- | --- | --- |
| `claim_review`(LangGraph) | 건 · 판정 단위 · 관련자 근거 → 추천(승인 · 반려 · 소명 먼저) · 결재권자 · 근거 · 반대 근거 · 확신도 | 가드가 합산 숫자 대조 · 결재 단계 올림 → 사람 결재 뒤 일치 기록 |
| `explanation_review`(LangGraph, 도구 5종) | 소명 회신 문장 → 주장별 조회 · 대조(일치 · 불일치 · 확인불가, 근거 행) → 증빙 충분 · 부족 | 도구가 돌려준 행만 근거로 인정 → 영업지원팀 확인 → 재판정 또는 지급보류 |
| `master_change_parser`(LangGraph) | 정정 신고 문장 → 대리점 · 속성 · 새 값 | 가드가 "문장에 그 글자가 있나" 확인 → 영업지원팀이 확인 · 수정해 적용 |
| 상계액 추천(단일 호출 + 가드) | 그룹 연체 채권 · 상계 한도 · 영업 의견 → 추천 상계액(0 ~ 한도) | 재무 결정 → 대리점 동의[모의] |

  LLM 키가 없거나 2회 실패하면 **대체 모드**로 규정 결과만 남기고 업무는 그대로 진행된다.

- **예상 효과의 산정 방식**: 금액은 원본 장려금 · 채권으로 계산(VAT 제외 원). 상계 금액 효과는 [가정] 기준(90일 · 동의) 아래의 결과다. 시간: gpt-5-mini 기준 AI 검토 약 13~16초, 상계 추천 12~19초, 소명 검토 약 43초, 정정 해석 4초(진짜 키로 측정, 11/15).
- **조건이 바뀌어도 타당한지**: 정정으로 그룹이 바뀌면 판정 · 승인 요청 · 상계 제안이 함께 다시 계산되고(열린 요청 · 제안은 취소), 그룹이 그대로면 근거 쌍과 함께 결론을 유지한다. 이미 돈이 나간 건은 바꾸지 않는다.

| --- | --- | --- | --- |

## 5. 실행 · 재현 방법

- **결과물 위치**: 배포 https://related-party-rebate-agent-h6nw.axhub.app (AXHub, Docker) · 소스 https://github.com/LeoChoi224/related-party-rebate-agent

- **설정**: `backend/.env.example` 을 `backend/.env` 로 복사해 `LLM_PROVIDER=openai`, `OPENAI_API_KEY` 를 넣는다. 비우면 AI 는 대체 모드로 돌고 업무 흐름은 그대로 동작한다.
- **로컬 실행**
  ```bash
  python -m pip install -r backend/requirements.txt
  npm --prefix frontend ci && npm --prefix frontend run build
  (cd backend && python -m uvicorn app.main:app --port 8000)   # http://localhost:8000
  (cd backend && python -m pip install -r requirements-dev.txt && python -m pytest -q)   # 447 passed
  ```
  Docker: `docker build -t rebate-agent .` → `docker run -p 8080:8080 rebate-agent`. macOS 에서 작업 폴더 그대로 빌드하면 한글 폴더 이름 정규화(NFD) 때문에 원본 COPY 가 실패할 수 있어, `git archive HEAD` 로 푼 폴더에서 빌드한다(AXHub 는 git 기준이라 문제없음).
- **원본 · 추가 데이터**: 원본은 `01_참가자_배포용/04_원본데이터/01_corevia`(수정하지 않음). 앱이 켜질 때마다 원본 CSV 4개로 SQLite 업무 DB 를 새로 만든다(`backend/app/seed`). 가정 · 모의 · 주장 데이터는 업무 DB 의 별도 표 · 행으로만 생기고, 화면에 [원본] · [주장] · [가정] · [모의] 배지로 구분된다.
- **대표 사례의 입력값과 실행 순서**: 오른쪽 위 역할을 "시연 관리자"로 → 시연 패널.
  1. 초기화 → 6월분 접수
  2. (변경 사례) D-041 주소 정정 — 일괄 전결보다 먼저 넣어야 재판정 2건이 보인다 / D-037 정산계좌 변경
  3. (정상) 단독 37건 전결 + 지급 지시 → 대기 중 지급 모두 은행 회신 성공 → 영업임원 G1 승인 → RB-00054 상세에서 역할을 바꿔 가며 영업 의견(영업지원팀) · AI 추천 · 재무 결정(재무) · 대리점 동의
  4. (거절) 초기화 → 6월분 접수 → 영업임원 G1 반려 + 소명 요청 → G1 소명 회신 넣기 → 각 건 상세 소명 칸에서 영업지원팀 확인
- **변경 조건 · 모의 회신 입력**: 정정 신고 화면(문장 또는 폼), 건 상세의 은행 회신 · 대리점 동의 · 소명 회신 버튼, 시연 패널.
- **결과 · 상태 · 기록 확인 위치**: 처리함(상태별), 건 상세(원본 기록 · 결재 경로 · 관련자 근거 · 승인 요청 · 상계 · 지급 · 이력), 작업(부서별), 이벤트 이력, AI 기록, 정정 신고 이력. API 는 `/docs`.
- **재실행 전 초기화와 현재의 제약**: 시연 패널 "초기화"(또는 앱 재시작)가 업무 DB 와 그래프 진행 위치를 원본 상태로 되돌린다. 제약: 역할은 화면에서 고르는 값(로그인 없음 — 권한은 서버가 역할 값으로 403 검사), 업무 DB 는 재시작 · 재배포 때 초기화, AI 요청은 LLM 응답 시간(수 초 ~ 수십 초)만큼 걸린다.
