## 3. 업무 모델 (온톨로지)

**객체**
- `Agency`: 대리점(D-nnn)
- `IdentityAttr`: 대표자, 주소, 등록계좌, 실입금계좌. 출처 파일과 기준 시점을 함께 기록한다.
- `RelationEdge`: 두 대리점 사이의 일치 관계. 일치한 속성 목록을 붙이고, 판정 결과(관련자 / 정황)를 둔다.
- `RelatedPartyGroup`: 관련자 그룹. **버전이 있다** — 마스터가 바뀌면 그룹을 다시 계산하고 새 버전을 만든다.
- `RebateClaim`: 월 장려금 1건(RB-nnnnn)
- `ApprovalRequest`: 승인 요청. 상신 대상, 그룹 합산액, 근거, 결과를 담는다.
- `ExplanationRequest` / `ExplanationReply`: 소명 요청과 회신
- `PaymentOrder` / `BankReply`: 지급 지시와 은행 회신
- `ARItem`: 미수채권
- `OffsetProposal`: 상계 제안
- `Task`: 부서별 작업
- `EventLog`: 누가, 언제, 무엇을, 왜 바꿨는지
- `AIRecommendation`: AI 추천 1건. 추천 내용, 근거와 반대 근거, 확신도, 코드가 계산한 최소 결재권자, 사람의 최종 결정과 추천 일치 여부를 담는다
- `ExplanationCheck`: 소명 회신에 담긴 주장 하나를 데이터와 대조한 결과(일치 / 불일치 / 확인 불가)

**RebateClaim 상태 흐름**
```
접수 → 관계확인 → ┬ 전결대기 ──────────────→ 승인 → 지급지시 → 지급완료
                 ├ 상신대기(영업임원) ─┬ 승인 ↗
                 │                    └ 반려 → 소명대기 → 재상신 | 지급보류
                 ├ 소명대기 → (회신) → 관계확인 다시
                 └ 상계검토(확장) → 상계확정 | 지급
재검토필요 ← (마스터 정정 / 그룹 버전 변경 이벤트)
```

**규칙**
- **R1 관련자 판정 [원본]**: 대표자·주소·계좌 중 2개 이상이 같으면 관련자다. 관계는 전이적으로 연결한다. 계좌는 등록계좌와 실입금계좌를 둘 다 대조한다.
- **R2 한도 [원본]**: 그룹 단위 월 합산이 200만원 이하이면 영업지원팀 전결, 넘으면 영업임원 승인.
- **R3 정황 [원본+가정]**: 속성 1개만 같으면 관련자가 아니다. 소명 요청 작업은 만들되 **지급을 중단하지는 않는다.** 원본이 일괄 지급중단을 정답으로 정하지 않았기 때문이다.
- **R4 재검토 [가정]**: 그룹 버전이 바뀌면 영향받는 미지급 건과 이미 승인된 건에 `재검토필요`를 붙이고 작업을 만든다.
- **R5 권한 [원본]**: 시스템은 한도를 넘는 건을 자동으로 확정하지 않는다. 항상 사람에게 상신한다.

## 4. AI·사람·도구 역할

### 4-1. 원칙
- **AI가 판단하고 추천한다. 최종 결정은 사람이 한다.** 근거는 원본 규정이다: "Agent는 위 경계를 넘는 결정을 **자동 확정하지 않고** 사람에게 상신한다" (approval_authority_policy **[원본]**). 규정이 막는 것은 자동 확정이지 AI의 판단이 아니다.
- **결재 경로 가드: AI는 결재 단계를 올릴 수는 있어도 내릴 수는 없다.** 코드가 규정상 최소 결재권자를 계산한다(그룹 월 합산 200만원 초과면 영업임원). AI가 이보다 낮게 판단하면 코드 값으로 고정하고, 그 불일치를 기록한다. 이유: "사람이 최종 결정한다"는 안전장치는 그 건이 **올바른 결재권자 앞에 도착해야** 작동한다. 1~5월 G1 15건은 개별 건만 보고 전결로 처리됐다(F3). AI가 같은 실수를 해도 막혀야 한다.
- **업무 상태는 DB 한 곳에만 둔다.** LangGraph 체크포인트에는 그래프가 어디까지 진행됐는지만 둔다. 상태를 바꾸는 것은 사람 결정 뒤의 `apply_decision` 노드뿐이다. 컨테이너가 다시 떠서 체크포인트가 사라져도, DB의 현재 상태에서 그래프를 다시 시작하면 된다.
- **LLM을 쓸 수 없으면 대체 모드로 돈다.** AI 추천 없이 규정 계산 결과만 보여주고, 사람이 직접 판단한다.

### 4-2. LangGraph 그래프 3개

| 그래프 | 시작하는 때 | 하는 일 | 사람 결정 지점 (interrupt) |
|---|---|---|---|
| `claim_review` | 장려금 건 접수, 재검토필요 | 조회 도구 → 규정 계산(코드) → AI 추천(전결 / 상신 / 소명 먼저 / 상계 검토) → 가드 검증 → 사람 결정 → 반영 → 후속 처리(외부 회신 대기) | 영업지원팀 또는 영업임원 (최소 결재권자 이상) |
| `explanation_review` | 소명 회신 도착 | 회신 속 주장 추출 → 주장마다 도구로 데이터 조회·대조(반복) → 타당성, 부족한 증빙, 추가 요청문 → 가드 검증 → 사람 확인 | 영업지원팀 |
| `master_change_parser` | 마스터 정정 신고 | 문장 → 구조화된 변경 → 대리점·속성·이전 값 검증 → 사람 확인 → 그룹 재계산 → 영향받는 건마다 `claim_review` 재실행 | 영업지원팀 |

- 그래프 실행 단위: **thread_id = 대상 건 ID**. 사람이 버튼을 누르면 API가 그 스레드를 이어서 실행한다.
- 가드 검증: ① AI 출력의 숫자가 코드 계산값과 같은가 ② 결재 단계가 최소 결재권자 이상인가 ③ 출력 형식이 맞는가. 숫자가 틀리면 1회 다시 생성하고, 2회 실패하면 대체 모드로 넘어간다.

**소명 대조 예시** (`explanation_review`가 왜 그래프여야 하는지 보여주는 사례):
> 회신: "D-024는 별도 법인이고, 계좌가 겹친 건 세무대리인이 대신 입금해서입니다." **[모의]**
> → 대조 1: D-024 입금 DP-00013·14의 계좌 = 국민 412-27-556310 = **D-011·D-037의 등록 정산계좌** (세무대리인 계좌 아님) **[원본]**
> → 대조 2: D-024와 D-011은 대표자(박상현)와 주소(성남시 상공로 128)도 같다 **[원본]**
> → AI 판단: 설명이 데이터와 맞지 않음. 추가 증빙(입금 대행 계약서, 세무대리인 계좌 명의) 요청을 추천

### 4-3. AI 추천을 보여주는 방식
- 추천과 함께 **근거 데이터(파일과 행)**, **반대 근거**, 확신도를 보여준다. 예: 반대 근거 "사업자번호는 서로 다름"
- 사람이 추천과 다르게 결정하면 **사유 입력을 필수**로 한다
- **AI 추천과 사람 결정의 일치 여부를 기록**한다 → 설계 설명서의 "확인할 개선 효과" 지표로 쓴다
- AI가 결재 단계를 낮게 판단해 코드가 올린 경우, 화면에 그 사실을 표시한다

### 4-4. 주체별 역할

| 주체 | 하는 일 |
|---|---|
| 코드(결정적) | 관련자 판정, 그룹 합산, **최소 결재권자 계산(가드)**, 상태 전이, 작업 생성. LangGraph의 도구와 노드로도 호출된다 |
| AI (LangGraph) | 장려금 건 추천, 소명 주장 대조와 판단, 정정 신고 해석. 상태는 직접 바꾸지 않는다 |
| 사람 | 영업지원팀(전결, 소명 확인, 정정 확인), 영업임원(상신 건 승인·반려), 재무(상계 승인, 지급 실행), 내부감사(과거 건 재검토) |
| 모의 외부 | 대리점 소명 회신, 은행 지급 회신, 대리점의 상계 동의 |

## 5. 필수 확장 — 지급 전 미수채권 대조와 상계 검토 [가정]

- **필요한 이유**: G1은 장려금을 받으면서 미수채권 4,848만원(120일 넘게 연체 5건)을 갖고 있다. 게다가 D-024의 채권은 G1 공유계좌로 입금됐다. 장려금 지급만 따로 보면 재무의 채권 회수 목표와 충돌한다.
- **동작**: 장려금 건이 `승인`되면 같은 그룹의 연체 채권을 조회한다. 기준(예: 90일 넘게 연체 [가정])을 넘으면 상계 제안을 만든다. 재무가 승인하고 대리점이 동의(모의)하면 지급액을 상계액만큼 줄이고, **확장 테이블의 채권 잔액**을 갱신한다. 원본은 건드리지 않는다.
- **판단이 바뀌는 지점**: 확장이 없으면 "현금 지급"으로 끝난다. 확장이 있으면 "상계 후 차액 지급 또는 지급 0원"이 된다.

## 6. 다른 부서 영향

- **재무(채권관리)**: 상계 제안을 받으면 회수 계획이 바뀐다. 연체 채권이 줄어든다.
- **영업**: 지급이 보류되거나 상계되면 대리점과의 관계에 부담이 생긴다. 영업 의견을 입력할 수 있게 하고, 그 의견에 따라 대안이 달라진다. 예: 부분 상계로 바꾸거나, 지급은 하되 회수 일정 약정을 받는 쪽으로 바꾼다.
- **내부감사**: 1~5월에 전결로 지급된 G1 15건(2,224만원)에 대해 사후 검토 작업이 생긴다.

## 7. 시연 시나리오 3개

1. **정상** — 6월분 40건을 일괄 접수한다. 37건은 전결 후 지급지시, 모의 은행 회신을 거쳐 `지급완료`가 된다. G1 3건은 합산 3,888,097원이라 영업임원에게 상신되고, 승인되면 상계 검토(확장)로 넘어간다. 재무가 승인하면 상태가 기록된다.
2. **조건 변경** — 마스터 정정 신고가 들어온다(예: "D-037 정산계좌 변경"). 등록계좌만 보면 D-037은 대표자 1개만 일치해 그룹에서 빠진다. 하지만 **실입금계좌(DP-00020)가 여전히 G1 공유계좌라서 그룹이 유지되고, 결론도 유지된다.** 화면에서 그 근거를 보여준다. 결론이 실제로 바뀌는 정정도 하나 시연한다. 예: "D-041 주소 정정 → D-034와 주소 일치" → 새 그룹 G2가 생기고, 6월 합산을 다시 계산해 승인 경로가 달라지는지 보여준다(수치는 구현 때 검증). 비교 기준: 그룹이 줄어든 G1' = {D-011, D-024}여도 6월 합산은 2,562,561원이라 여전히 상신 대상이다.
3. **정보 부족·거절** — 영업임원이 "소명 먼저"를 이유로 반려한다. 시스템이 소명 요청을 보내고 모의 회신을 받는다(예: "같은 대표의 별도 법인, 계좌는 세무대리인이 대납"). `explanation_review`가 회신의 주장을 입금 기록과 대조해 **설명이 데이터와 맞지 않음**을 찾아내고(4-2 예시), 추가 증빙 요청을 추천한다. 영업지원팀이 확인하면 상태는 `지급보류`가 된다. 보완 회신이 오면 `claim_review`가 다시 돌고 재상신된다.
